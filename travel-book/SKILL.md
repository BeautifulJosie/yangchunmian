# Travel Book 生成指南

这份 SKILL.md 和 `template/index.html` 配套使用。把这个仓库整个交给你自己的 AI（Claude Code、Cursor
之类能读写文件的工具都行），再把这次旅行的资料发给它，让它照着下面的规范把 `template/index.html`
改写成这次旅行专属的页面——**改的是内容，不是结构**，`template/index.html` 里已经写好的交互组件和
插画（见第 2 节）直接复制粘贴改文字/改地标就行，不用重新设计。

生成完是一个**单文件、零依赖**的 HTML，用手机浏览器直接打开就能看，怎么发布见第 5 节。

## 0. 开始前，先问清楚这几件事

- 目的地、日期、人数、进出交通方式（航班号/车次，几点到几点）
- 已经订好的机票/租车/酒店/门票——发确认信息过来，没订好的先留"待定"
- 每天大致想去哪、按什么顺序

资料不全不用等，缺的地方直接标"待定"生成第一版，之后随时可以回填。

## 1. 页面结构（自上而下，固定顺序，别打乱）

1. **顶部插画头图**：挑这次目的地 2~3 个最有辨识度的地标剪影（建筑/自然景观），拼成一幅简化的
   横版场景插画，配云、山、太阳/月亮这些简洁元素——见第 2.0 节，照着 `template/index.html` 里
   大阪城+五重塔+鸟居那份改地标就行，画法别推翻重来。
2. **Hero**：emoji + 标题、日期/人数/进出交通一行小字、状态徽章（机票/酒店 n/n/门票这类）。
3. **NOW 卡片**（紧跟 Hero）：
   - 脉冲圆点 + "此刻关注 · NOW"
   - 自动算出的**下一个行程事件**标题 + 一行 meta
   - 大号等宽倒计时，每秒跳动
   - 底部一行"当前待办" = 清单里第一条未勾选项，点击跳到待办清单
   - 由页面底部 `EVENTS` 数组驱动，旅行全程自动推进，不用每天手动改"现在是第几天"
3. **顶部锚点导航**：总览 / 航班 / 每日行程 / 待办清单 / 贴士，够用就行，模块不全就删掉对应的锚点。
4. **行程总览**：路线整体是怎么走的。**默认按第 3 节画一张真实地形轮廓 + 按天上色的路线图**，
   这是效果最好的版本，别一上来就退到纯文字——只有时间/资料实在不够时才用文字路线概述兜底。
5. **航班/交通卡片**：时间、班次号、大概时长。**确认号只写"见邮件"，不要写在页面里**——
   一旦发布出去有链接，任何拿到链接的人都能看到，确认号+姓氏很多时候就能改签别人的票。
6. **每日行程卡**：左边时间列 + 右边内容，需要预约/买票的标签提醒，亮点项目标出来，
   底部一行"今晚住哪"。**每一条时间项都配一句 `<small>` 描述**（见 2.2.1），别只写地名和时间——
   这一句才是让页面"读起来丰富"的关键，比地图和配色都重要。**明确知道两个点之间路程时长的，
   在中间插一条 `.tl-gap` 时长胶囊**（见 2.7），不知道/不重要的跳过就好，不用硬凑。
7. **待办清单**：分组列 + 打勾，勾选状态存 `localStorage`，已确认的事项预先锁定为完成状态
   （见第 2.4 节 `data-locked`），顶部放进度条。
8. **贴士** + footer：天气、排队预期、交通提醒收尾。footer 写**这次旅行本身**的信息
   （项目名 · 目的地 · 人数，参考 `Travel Book · 日本关西六日 · 2 人行` 这种），**不要写实现细节**——
   "单文件零依赖""数据仅存在浏览器里"这类话是说给开发者听的，游客翻到页面底部不需要看这些，
   写出来会显得很怪。真要提隐私提醒，放进"贴士"里用人话说（比如"这份行程链接谁都能打开，
   不想被看到的内容自己删掉"），不要塞进 footer。

## 2. 已经写好的组件和插画（复制粘贴，不用重新发明）

`template/index.html` 里已经有一份可运行的示例，演示了下面这些模式：

### 2.0 顶部插画头图 —— 地标剪影场景

`.hero-scene` 是一整块手绘风格的 SVG 横版插画，画法是"分层剪影"：天空渐变（`#skyGrad`）垫底，
依次叠云朵（`.scene-cloud`）、太阳/月亮（`.sun-ico`/`.moon-ico`/`.star-ico`，CSS 按深浅色模式
自动切换显示哪个，不用手动判断）、远山（`.scene-ridge`）、2~3 个地标剪影（`.scene-fig`，
统一用一个颜色变量 `--scene-fig` 画实心剪影）、两侧的树（画面边框）、底部地面色块。

换目的地时：

- 保留这套分层结构和配色变量（`--sky-top`/`--sky-bottom`/`--scene-fig`/`--scene-sun`/`--scene-moon`），
  **只换地标剪影的具体形状**——挑这次目的地 2~3 个最有辨识度的建筑/自然地标（地标性建筑、山峰、
  知名桥梁、灯塔这类轮廓一眼能认出的），参考 `template/index.html` 里大阪城（阶梯状天守阁）、
  五重塔（层叠收窄的塔身）、鸟居（两根柱子+上下两道横梁）的画法，用简单几何形状（矩形堆叠、
  三角形屋顶、简单路径）拼出新地标的剪影，不用追求精细写实。
- 地标剪影之间留出呼吸空间，别互相重叠；每个地标用 `<g class="scene-fig">` 包一层，颜色自动跟随
  主题变量，不用每个地标单独配色。
- 画完用 Playwright 截图检查浅色（白天）和深色（夜晚）两种状态，确认地标轮廓清楚、没有元素穿帮
  或者比例明显失真（这是容易出错的地方，宁可形状简单一点也要保证"看着像那个地方"）。
- 如果实在想不出合适的地标组合，或者目的地没有特别有辨识度的建筑，可以只画山峦+云+太阳/月亮
  这种纯自然风景剪影，不强求一定要有建筑地标。

### 2.1 `.pin` —— 点地名跳导航

```html
<a class="pin" href="https://www.google.com/maps/search/?api=1&query=Osaka%20Castle" target="_blank" rel="noopener">大阪城</a>
```

用 Google 地图的搜索链接就够，不用接地图 SDK。没有固定地址就用搜索词（比如店名），
Google 会自动解析到最近的一家。

### 2.2 `.info-btn` / `.info-panel` —— 点 ⓘ 展开地点简介

```html
<a class="pin" href="...">道顿堀</a>
<button class="info-btn" type="button" data-target="info-dotonbori" aria-expanded="false" aria-label="道顿堀简介">ⓘ</button>
<div class="info-panel" id="info-dotonbori" hidden><p>两三句考证过的简介：历史/规模/值得看的细节。</p></div>
```

`id` 和 `data-target` 要一一对应且全页唯一。简介写 2~4 句真实信息，不是随便编。

#### 2.2.1 每条时间项都要有的 `<small>` 一句话描述（这条不是可选项）

`.info-btn`/`.info-panel` 是"点了才展开"的深度背景介绍；除此之外，**每一条 `.tl` 时间项自己都要带一句
默认可见的 `<small>` 描述**，不需要点击。这句话解决的是"这一项具体要干嘛/为什么这么安排"，
跟 `.info-panel` 的历史背景是两回事：

```html
<div class="tl"><span class="t">14:30</span><div class="tx">
  <a class="pin" href="...">Church's Chicken</a> <span class="tag star">⭐ 快餐</span>
  <small>点开导航会自动找离你们当前路线最近的一家；垫一口就够，晚餐 17:45 还有正餐</small>
</div></div>
```

哪怕这一项没有 `.pin`/`.info-btn`（比如纯粹的驾驶/等待/备注类时间项），也照样配一句 `<small>`。
没有这一句，页面会退化成一张干巴巴的时间表——`<small>` 才是撑起"读起来丰富耐看"的主要内容，
比地图配色更重要，宁可少画地图细节也不能省这一句。

### 2.3 `.dm-toggle` / `.dm-frame` —— 当天完整路线地图（点了才加载）

```html
<button class="dm-toggle" type="button"
  data-src="https://maps.google.com/maps?saddr=起点&daddr=途经点1+to:终点&output=embed">🗺️ 展开今日路线地图</button>
<a class="dm-go" href="https://www.google.com/maps/dir/?api=1&origin=起点&destination=终点&travelmode=driving&waypoints=途经点1%7C途经点2" target="_blank" rel="noopener">Google 导航 ↗</a>
```

多途经点路线用 `waypoints=A%7CB%7CC`（`%7C` 是竖线 `|` 的编码）。不预加载，点了才灌 `<iframe>`，
避免每天都加载地图拖慢首屏。

### 2.4 `.day-toggle` / `collapsed` —— 每日行程卡折叠

点 `.day-head` 整卡折叠/展开，JS 已经写好了。**某一天真正过去之后**，给对应的
`<div class="card day">` 加上 `collapsed` class（`<div class="card day collapsed">`），
页面默认打开时只留正在进行和接下来的天数在眼前，不用每次都手动展开。

### 2.5 待办清单的 `data-locked`

已经确认/订好的事项，给 `.todo` 加 `data-locked="1"`：显示为固定打勾状态，不受用户本地
勾选影响、也不占用 `localStorage`。没锁定的正常项用户自己点了才算勾选，状态存本机。

### 2.6 待办清单：可选的跨设备/跨好友同步

默认待办清单是纯本地的（`localStorage`，只在当前浏览器生效）。`template/index.html` 底部预留了
一个 `SYNC` 配置对象和一段"大家一起加"的共享待办区（可以自由添加、编辑、删除、勾选），默认关闭。

用户如果明确要求"发出去后不同人能互相同步待办/协作编辑"这类效果，按
`optional/supabase-sync/README.md` 的步骤配一个免费 Supabase 项目（建表 + 拿连接信息），
再填好 `supabaseUrl`/`supabaseAnonKey`/`tripId` 三项即可，不需要改其他代码——`SYNC.enabled`
默认就是 `true`，但只要 `supabaseUrl`/`supabaseAnonKey` 还是空字符串就不会真的发起连接，
页面会一直安全地停留在本地模式。没有同步需求就不用管这三项，保持空字符串即可。

### 2.7 `.tl-gap` —— 两个时间项之间的路程时长胶囊

```html
<div class="tl-gap"><span class="gt"></span><span class="chip">🚶 步行约 15 分钟</span></div>
```

插在两条 `.tl` 之间，`.gt` 是一条跟时间列对齐的短竖线（视觉上续着时间轴），`.chip` 是居中的小胶囊，
写交通方式 + 大概时长就行（步行/电车/打车，"约 X 分钟"）。只在**明确知道、且对安排有参考价值**的
相邻两站之间加，不知道准确时长或者本来就在同一个地方（不涉及移动）不要硬编一个数字糊弄。

## 3. 地图画法（默认做，`template/index.html` 已经演示了一份完整效果）

`template/index.html` 的行程总览就是这种效果：真实地形轮廓（哪怕简化，也大致认得出方位）+
按天上色的路线 + 指北针 + 虚线飞行段 + 图例。这是**默认应该做到的水准**，不是加分项——
之前版本里那种"几个点连一条抽象曲线、不像任何真实地方"的画法已经不再是推荐做法，别退回去画那种。

### 3.1 轮廓怎么画

- 等距圆柱投影：`x=(lon-lonMin)*S*cos(中心纬度)`，`y=(latMax-lat)*S`
- 手工挑数十个边界经纬点画轮廓，城市/途经点用真实经纬度投影；没有精确经纬度数据时，
  凭对这个地方大致地形（海岸线、半岛、山脉走向）的了解手绘一版简化轮廓也可以——
  重点是"看着像那个地方"，不是测绘级精度。`template/index.html` 里那份关西轮廓就是这么画的。
- **写一个 Python 脚本批量算好坐标再贴进 SVG**，不要在页面里用 JS 运行时现算
- 完成后截图检查浅色/深色模式下标签有没有被裁切或重叠

### 3.2 按天上色的路线 + 图例（跟 `template/index.html` 保持一致的做法）

- 每天的移动路线配一个颜色（`.route.r1`/`.r2`/`.r3` 这种 class，颜色来自 CSS 变量，深色模式
  自动换成对应的浅色调），同一物理路段重复走（比如去程和原路返回）要把两条线稍微偏移几像素，
  别完全重叠成一条。
- 城市/景点用 `.node`/`.node-ring`/`.node-halo` 画点，`.node-halo` 是垫在下面的纯色圆，
  避免文字标签被地形颜色吃掉看不清。过夜天数多的地方点画大一点（`.node-ring`），
  当天往返不过夜的地方画小一点、不加外圈（`.node-day`）。
- 进出的航班画成地图边缘之外的虚线（`.flight-ln`），旁边配一行小字写清楚哪天飞来/飞走。
- 指北针（`.compass`）放在地图空白角落。
- **图例放在 SVG 外面的普通 HTML 里**（`.legend`，颜色小色块 + 文字），不要把每段路线的时长
  之类的说明也塞进 SVG 里变成一堆小气泡——地图本身只留必要的方位信息，细节交给图例。

### 3.3 什么时候可以简化

资料非常简单（比如只有一个城市、没有跨城市移动）或者用户明确说不需要地图时，可以退到一段
文字路线概述。但只是"退到文字"，不要退到画一个不对应任何地方的抽象装饰图形——那种效果
比纯文字还差，用户已经反馈过这个问题。

## 4. 行程编排原则

- **以已经订好的交通时刻为准**往前往后排，宁可整体平移也不要硬塞——
  下午落地就当晚安排就近的项目，清晨航班就前一晚玩完、住机场方向。
- 长途路程标注中途休息点，避免深夜赶路。
- 核对沿途景点的开门时间、闭馆日、是否需要提前订时段票（很多免费景点也要）。
- **热门项目查一下会不会卖光，卖光了给替代方案**，别到了现场才发现进不去。
- 没订好的酒店/门票先在行程卡放"待定"、进待办清单，订好了回填。

## 5. 怎么发布

生成完第一版、用户确认内容没问题之后，**主动问一句要不要现在就部署成一个公网链接**——
默认生成的只是本地文件，用户自己打不开链接分享给同行的人。别等用户想起来问，生成完就问。

用户说不需要（比如只想自己留着、之后再发），就到此为止；用户确认要部署，按下面 Cloudflare Pages
的步骤直接带他做完，不用列一堆选项让他自己选：

### Cloudflare Pages（推荐，免费，带用户走一遍这个）

1. 让用户打开 https://dash.cloudflare.com 注册/登录（免费账号即可）。
2. 左侧 **Workers & Pages → Create → Pages → Connect to Git**，授权并选中这个仓库
   （需要用户自己在浏览器里点，Agent 没法代替他登录/授权）。
3. Build settings 里：
   - Framework preset 选 **None**
   - Build command 留空
   - **Build output directory 填 `template`**（不是留空、不是 `/`）——这样部署出来的网站首页
     就是改好的 `template/index.html`，不会展示这个模板项目自己的介绍页
4. **Save and Deploy**，几十秒后拿到一个 `*.pages.dev` 的公网链接，发给用户。
5. 告诉用户：以后每次这个仓库有新的 push，Cloudflare 都会自动重新构建部署，不用手动做任何事——
   旅行途中让 Agent 继续改行程、push 上去，线上链接会自动更新。

其他选项（用户明确要求别的方式再用，不用主动介绍）：

- **GitHub Pages**：仓库 Settings → Pages，发布源同样要指到 `template` 这个子目录
  （GitHub Pages 的简单界面只支持根目录或 `/docs`，指不了任意子目录时，退而求其次把
  `template/index.html` 的内容复制到仓库根目录的 `index.html` 里）。
- **Netlify / Vercel**：拖一个文件夹进去就能上线，同样注意发布的是 `template` 目录。
- 完全不部署：改完直接把 `template/index.html` 这个文件用微信/邮件发给同行的人，手机打开就能看，
  只是没法「一个人改了大家都看到最新版」。

**发布前检查一遍页面里有没有确认号、门锁密码这类敏感信息**——只要有公开链接，任何拿到链接的人
都能看到整份行程。

## 6. 旅行进行中怎么维护

旅行开始后，用户可能会随时说"这个订好了""改去另一个地方了""今天已经过去了"。这些情况回去改
`index.html`（不用整页重写，只改对应位置）：

- **二选一定案了**：删掉落选项（连同它的 `.pin`/`.info-btn`/`.info-panel`），保留项加一个
  `<span class="tag star">✓ 已吃/已访问</span>`；`EVENTS` 数组、当日路线概述、地图链接里
  凡提到过落选项名字的地方一并改掉，改完搜一遍确认没有残留。
- **预约/门票确认了**：行程卡里的标签从"需约/可选"改成"✓ 已预约/已访问"；对应待办项加
  `data-locked="1"`。
- **一天过去了**：给对应 `.card.day` 加 `collapsed`（见 2.4）。

**页面永远保持能直接读的最新状态**：不要在页面里放修改日志、"这次改了什么"之类的版本说明，
变更说明写在 git 提交信息里就够了——页面任何时候打开都是一份能直接看的最新版本。
